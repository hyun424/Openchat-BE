# 2026-05-03 작업 요약

작성일: 2026-05-03

## 1. 오늘의 목표

오늘은 OpenChat의 핫룸 성능 목표를 단순한 "연결 가능한 사용자 수"가 아니라 사용자 체감 기준으로 다시 잡았다.

핵심 목표는 다음과 같았다.

- 500명 단일 핫룸에서 메시지 저장, ack, live 표시가 안정적인지 확인한다.
- 500명 방이 여러 개 동시에 생겼을 때 현재 구조가 어디서 흔들리는지 측정한다.
- 결과를 바탕으로 다음 아키텍처 방향을 정한다.

## 2. 단일 핫룸 기준선

`ack-first + async live publish + outbox recovery` 구조에서 500명 단일방 기준선을 만들었다.

| 지표 | 결과 |
|---|---:|
| WebSocket 연결 성공률 | 100% |
| HTTP error | 0% |
| `chat_ack_roundtrip_ms p95` | 61ms |
| `ws_visible_freshness_ms p95` | 208ms |

이 구조의 의미는 다음과 같다.

- `chat.ack`는 DB commit 성공을 의미한다.
- Redis publish와 전체 fanout 완료는 ack 의미에 포함하지 않는다.
- live publish는 DB commit 이후 비동기로 즉시 시도한다.
- outbox는 live publish 주 경로가 아니라 실패 복구 경로로 둔다.
- `lastMessage`, `hotchat` 업데이트는 저우선순위 buffer로 분리한다.

이 기준선은 단일 500명 방에서는 사용자 체감 기준으로 가능성이 있다고 판단했다.

## 3. 500명 x 3개 핫룸 측정

다음으로 500명 방 3개가 동시에 활성화되는 상황을 측정했다.

| 항목 | 값 |
|---|---:|
| 방 수 | 3 |
| 방별 사용자 수 | 500 |
| 총 VU | 1500 |
| connect ramp | 120초 |
| chat duration | 120초 |
| send interval | 1000ms |

전체 결과는 다음과 같았다.

| 지표 | 결과 | 판단 |
|---|---:|---|
| WebSocket 연결 성공률 | 100% | 통과 |
| HTTP error | 0% | 통과 |
| `chat_ack_roundtrip_ms p95` | 385ms | 목표 미달 |
| `ws_visible_freshness_ms p95` | 75.891s | 크게 실패 |
| 송신 메시지 수 | 178,933 | 측정됨 |
| ack 수신 수 | 178,502 | 일부 차이 있음 |

방별 결과는 거의 비슷했다.

| 방 | ack p95 | visible freshness p95 |
|---|---:|---:|
| room-0 | 387ms | 75.843s |
| room-1 | 387ms | 75.928s |
| room-2 | 383ms | 75.938s |

특정 방 하나만 문제가 생긴 것이 아니라, 세 방 모두 같은 정도로 느려졌다. 따라서 병목은 방 하나의 문제가 아니라 공유 자원 또는 전역 처리 경로에 있다고 판단했다.

## 4. 병목 판단

WebSocket lane 자체는 주 병목이 아니었다.

| 서버 내부 지표 | p95 |
|---|---:|
| `ws.broadcast.lane.queue_wait` | 약 1.0ms ~ 1.2ms |
| `ws.broadcast.lane.worker.total` | 약 0.6ms ~ 0.7ms |
| `ws.broadcast.lane.send.total` | 약 0.2ms |
| `subscribe.redis.fanout_call` | 약 0.02ms 이하 |
| `fanout.total` | 약 0.014ms 이하 |

반대로 live publish 경로는 크게 밀렸다.

| App | live publish queue max |
|---|---:|
| app-1 | 18,533 |
| app-2 | 20,176 |
| app-3 | 19,472 |
| app-4 | 18,870 |

Redis publish 자체는 p95 약 0.8ms 수준으로 빠르지만, live publish executor의 전체 처리량이 여러 핫룸의 메시지량을 따라가지 못했다.

저장 경로도 ack에 영향을 줬다.

| 지표 | p95 |
|---|---:|
| `ingest.outbox_save` | 약 71ms ~ 75ms |
| `ingest.persist.total` | 약 100ms ~ 105ms |
| `ack.after_commit` | 약 0.1ms |
| `ws.control.ack.send` | 약 0.09ms |

ack 전송 자체는 빠르지만, DB 저장과 outbox 저장 transaction이 다중 핫룸에서 압박을 받으면서 사용자 기준 ack p95가 385ms까지 올라갔다.

## 5. 오늘 얻은 결론

현재 구조는 500명 단일방은 가능성이 있지만, 500명 방 3개를 사용자 체감 기준으로 처리하기에는 부족하다.

중요한 점은 연결 수 자체가 문제가 아니라는 것이다.

- 1500 WebSocket 연결은 유지됐다.
- HTTP error도 없었다.
- WebSocket lane/send도 거의 밀리지 않았다.
- 문제는 live publish executor, outbox 상태 마킹, DB 저장 경로가 여러 핫룸에서 전역 공유 병목이 되는 점이었다.

따라서 다음 개선은 WebSocket lane 수를 더 늘리는 방향이 아니다. API/Realtime 역할 분리와 room 단위 격리로 가는 것이 더 타당하다.

## 6. 다음 방향

다음 구조 방향은 `Realtime Data Plane` 분리다.

1차에서는 별도 서비스로 완전히 나누지 않고, 같은 Spring Boot 앱을 실행 역할로 나눈다.

```text
API node
-> REST API
-> login / room / message sync

Realtime node
-> WebSocket session
-> inbound chat save
-> ack
-> async live publish
-> Redis subscribe / fanout
```

1차 원칙은 다음과 같다.

- `APP_NODE_ROLE=api|realtime|all` 같은 역할 설정을 둔다.
- API VM과 Realtime VM을 Terraform에서 분리한다.
- Nginx는 `/api/**`는 API upstream, `/ws/chat`은 Realtime upstream으로 라우팅한다.
- WebSocket 메시지 저장은 1차에서는 Realtime 노드가 유지한다.
- Kafka나 Redis Stream 기반 저장 위임은 이번 단계에서 넣지 않는다.

이후에도 병목이 남으면 다음 단계는 room ownership이다.

```text
roomId -> owner realtime worker
```

이 구조로 가면 특정 핫룸의 live publish queue가 다른 방 전체를 같이 밀어내는 문제를 줄일 수 있다.

## 7. 포트폴리오 관점 정리

오늘 작업은 "무작정 스펙을 키워서 해결"이 아니라, 부하테스트 결과를 기준으로 병목을 분해하고 다음 아키텍처 방향을 정한 작업이다.

포트폴리오에서는 다음 문장으로 정리할 수 있다.

> 500명 단일 핫룸에서는 ack p95 61ms, visible freshness p95 208ms를 달성했지만, 500명 x 3개 핫룸에서는 visible freshness p95가 75.891초까지 악화됐다. 지표 분석 결과 WebSocket 연결이나 socket send가 아니라 live publish executor와 outbox/DB 저장 경로가 공유 병목임을 확인했고, 이를 근거로 API 계층과 Realtime data plane을 분리하는 방향으로 확장 계획을 수립했다.
