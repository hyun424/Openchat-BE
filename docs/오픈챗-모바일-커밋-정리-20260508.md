## 커밋 흐름

### `a924cca feat: automate partition lifecycle scaling`

이번 세션의 메인 커밋이다.

구현한 것:

- 자동 partition lifecycle scheduler 추가
  - 설정 기본값은 운영에서 disabled
  - `app.room-partition.lifecycle.enabled=true`일 때만 실행
  - Redis lease로 여러 노드 중 하나만 action 수행
  - Redis cooldown으로 room별 중복 scale action 방지
- scale-up 자동 실행
  - workload summary의 `SCALE_UP_CANDIDATE`를 사용
  - stable observation 조건을 만족한 hot room만 처리
  - state가 `ACTIVE`이고 target이 현재 partition보다 클 때만 scale-up
  - `scaleUp()` 후 reconnect 재분산 요청
  - `completeScaleUp()`으로 `SCALING_UP -> ACTIVE` 복귀
- 기존 연결 재분산
  - `RoomPartitionRedistributionService` 추가
  - scale-up 직후 기존 partition 범위에 `room.reconnect` control 발송
  - publish 실패는 scale-up rollback 사유로 삼지 않고 metric/log만 남김
- scale-down / drain 자동 실행
  - auto-managed room만 기본 대상
  - 낮은 workload가 stable window를 만족하면 high partition id부터 drain
  - 신규 route는 draining partition을 피함
  - draining partition session count가 cluster-wide 0으로 연속 관측되어야 complete
  - complete 후 `partitionCount` 감소 및 `ACTIVE` 복귀
- drain progress snapshot 확장
  - node snapshot에 local draining partition session count 추가
  - cluster summary에서 `roomId + partitionId` 기준 합산
  - 기존 JSON에는 새 필드가 없어도 빈 리스트로 처리
- lifecycle metric 추가
  - `openchat_room_partition_lifecycle_event_total`
  - low cardinality tag만 사용
- k6 reconnect 처리 추가
  - `room.reconnect` control frame 감지
  - 기존 socket close 후 `/ws-route` 재호출
  - 새 partition으로 재접속
  - route response의 `partitionCount`, `partitionId`, `routeVersion` 기록
  - reconnect 직전 pending ack 유실을 막기 위해 짧은 drain delay 적용
- GCP loadtest profile 추가
  - `infra/gcp-loadtest/profiles/room-partition-auto-lifecycle-smoke.tfvars.example`
  - 100 VU에서 lifecycle이 실제 발생하도록 threshold/stable window 조정
- 설계 문서 추가
  - `docs/room-partition-auto-lifecycle-20260508.md`

## 기반 커밋 맥락

### `c465724 fix: make room partition state initialization idempotent`

이전 작업에서 만든 기반 커밋이다. 첫 방 route 시점에 동시에 `room_partition_state` lazy insert가 들어오며 duplicate key성 500이 날 수 있던 문제를 막았다.

핵심:

- `RoomPartitionStateRepository.insertIfAbsent(...)`
  - MySQL `INSERT ... ON DUPLICATE KEY UPDATE room_id = room_id`
  - 이미 있으면 no-op
- `getOrInitialize()`
  - missing state면 `insertIfAbsent()` 후 다시 조회
- `getOrInitializeForUpdate()`
  - 먼저 row 존재 보장 후 `findByIdForUpdate()`
- `ensureInitialized(roomId)`
  - 신규 방 생성 시 partition state 선생성
- `RoomService.createRoom()`
  - 저장된 room id로 `ensureInitialized()` 호출

의미:

- 신규 방은 첫 `/ws-route` 전에 기본 partition state를 갖는다.
- 그래도 기존 방/누락 row는 DB upsert fallback으로 안전하게 복구된다.
