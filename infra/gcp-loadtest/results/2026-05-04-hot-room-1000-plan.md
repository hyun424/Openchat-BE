# 1000명 단일방 병목 확정 기록

## 목적

`500명 x 3방`에서 서버 fan-out/send 병목이 재현되지 않았으므로, 다음 실험은 바로 `1000 x 3`으로 가지 않고 `1000명 단일방`부터 확인한다.

이 실험은 한 방 fan-out 규모가 1000명으로 커질 때 서버 WebSocket lane/send 단계가 밀리는지 확인하기 위한 것이다.

## 구현 내용

- profile: `infra/gcp-loadtest/profiles/hot-room-1000-role-split.tfvars.example`
- scenario: `k6/scenarios/08-hot-room-ramped.js`
- topology:
  - API 1대: `e2-standard-4`
  - Realtime 4대: `e2-standard-8`
  - LB: `e2-standard-2`
  - MySQL: `e2-standard-4`
  - Redis: `e2-standard-4`
  - k6 1대: `e2-standard-16`
  - Monitoring: `e2-standard-2`
- load:
  - `vus_list=1000`
  - `connect_ramp_seconds=120`
  - `chat_duration_seconds=120`
  - `send_interval_ms=1000`
- disk:
  - SSD quota 250GB 안에 들어오도록 축소값 사용
  - monitoring 포함 예상 SSD: 약 200GB
  - monitoring 포함 예상 vCPU: 약 64 vCPU

## 측정 주의사항

- `08-hot-room-ramped.js`의 per-received detail metric은 기본 비활성화했다.
- `HOT_ROOM_DETAIL_METRICS=true`를 주면 기존 detailed counter를 다시 켤 수 있다.
- `visible freshness`는 `k6/lib/ws.js`의 sampling/aggregation 설정 영향을 받는다.
- k6 log에 InfluxDB `413` 또는 flush 지연이 반복되면 그 실행은 병목 판정에 사용하지 않는다.

## 결론

`1000명 단일방`에서는 서버 WebSocket fan-out/send 병목이 확인되지 않았다.

근거:

- 서버 `ws.broadcast.lane_done` p95가 `121ms`이고 max도 `127ms`다.
- 서버 ack p95가 `21ms`로 낮다.
- k6 visible freshness p95도 `215ms`다.
- 연결 성공률은 `100%`이고 HTTP error rate는 `0`이다.

따라서 이번 결과만 놓고 보면 500명에서 보이지 않았던 병목이 “한 방 fan-out 1000명”에서 새로 발생했다고 보기 어렵다. 다음 실험은 `1000 x 3` aggregate 부하로 넘어가서 방 3개 합산 처리량에서 병목이 생기는지 확인하는 쪽이 맞다.

다음 실험에서 봐야 할 것:

- `1000 x 3`에서 서버 `ws.broadcast.lane_done` p95/max가 1초 이상으로 커지는지
- `1000 x 3`에서 k6 visible freshness만 높고 서버 pipeline은 낮은지
- `1000 x 3`에서 outbox/live publish/Redis fanout 쪽 stage가 먼저 커지는지
- k6 worker를 단일로 둘 때와 3대로 나눌 때 관측값이 달라지는지

## 실측 TPS 재측정 및 한계 탐색

### 목적

이번 재측정의 목적은 “1000명 처리 가능”처럼 인원수만 말하지 않고, 같은 시간축에서 다음 값을 분리해 확인하는 것이다.

- 입력 TPS: 서버가 받은 채팅 메시지 수/sec
- DB 저장 TPS: DB에 저장된 메시지 row/sec
- WebSocket delivery TPS: 서버가 WebSocket으로 fan-out delivery를 성공 처리한 수/sec
- 네트워크 egress: WebSocket send bytes/sec 기준
- 지연: k6 visible freshness와 서버 `ws.broadcast.lane_done`

이번 결과는 `100만 TPS`가 아니다. 한 사람이 보낸 메시지가 같은 방의 여러 사용자에게 전달되므로, 입력 TPS와 delivery TPS는 다른 값이다.

### 변경된 측정 방식

- k6 send payload에 `clientSentAt`과 run label 기반 `clientMessageId`를 넣었다.
- 서버에 WebSocket send attempted/succeeded/failed/bytes/duration metric을 추가했다.
- DB 저장은 `client_message_id LIKE '<run-label>-%'` row count로 검증했다.
- k6는 close 직전 전송 손실을 줄이기 위해 send 종료 후 drain 시간을 둔 뒤 socket을 닫는다.
- Prometheus summary는 30초 window 기준 peak/avg rate를 기록한다.
- `HOT_ROOM_DETAIL_METRICS=false`로 per-message detail metric은 기본 비활성화했다.

### 실행 조건

- API: `e2-standard-4` x 1
- Realtime: `e2-standard-8` x 4
- 앱 서버 합계: `36 vCPU / 144GB`
- k6: `e2-standard-16` x 1
- LB/MySQL/Redis/Monitoring: 기존 role-split profile과 동일
- 시나리오: 단일 hot-room, `connect_ramp_seconds=120`, `chat_duration_seconds=120`, `send_interval_ms=1000`
- Grafana: `http://34.64.50.210:3000`

### 판정

1500명 단일방까지는 서버 WebSocket fan-out/send 병목이 명확히 나타나지 않았다. 1800명 단일방은 사용자 체감 지표와 k6 ack 관측 지표가 기준을 넘었기 때문에 현재 조건의 한계 후보로 본다.

근거:

- `ws.broadcast.lane_done` p95가 1800명에서도 `201ms`로 `1s`보다 낮다.
- `ws.send.duration` p95도 `0.2ms` 미만이다.
- k6 visible freshness p95는 1500명까지 `291ms`였지만, 1800명에서 `617ms`로 기준을 넘었다.
- 1500명까지는 k6 sent, ack count, DB row count가 모두 일치했지만, 1800명에서는 `214,842 / 214,728 / 214,807`로 불일치했다.
- 1800명에서 서버 ack p95는 `56ms`인데 k6 ack p95는 `2143ms`라서, 서버 ingest/ack 자체보다 k6 수신/관측 경로 또는 close/drain 경계 영향이 섞였을 가능성이 높다.
- 1800명에서 delivery TPS peak는 `143.8k/s`로 1500명의 `143.2k/s`와 거의 같아졌다. 입력 TPS는 증가했지만 delivery peak가 더 오르지 않았고 visible p95가 악화됐으므로, 이 지점부터는 측정 경로와 delivery 처리 한계를 분리해서 봐야 한다.

현재 조건에서 안정적으로 말할 수 있는 값은 “36 vCPU 앱 서버가 1500명 단일방에서 peak 입력 약 `1.4k msg/s`, peak WebSocket delivery 약 `143k sends/s`, peak egress 약 `373Mbps`를 처리했고, visible p95가 `300ms` 안팎이었다”는 것이다.

1800명은 `visible p95 >= 500ms`, `ack p95 >= 300ms`, DB row mismatch, `ws.send.failed` 증가 조건을 동시에 만족했기 때문에 2000명은 실행하지 않았다. 다음 단계는 2000명 증량이 아니라, 1800명 지점에서 다음 중 무엇이 주원인인지 분리하는 것이다.

- 같은 1800명 단일방을 k6 worker 2대로 나눠 관측해서 k6 단일 관측 병목인지 확인한다.
- 서버 Prometheus 기준 delivery TPS가 왜 `143k/s` 근처에서 plateau가 생기는지 확인한다.
- `ws.send.failed`가 close-boundary인지, 실제 전송 실패/닫힌 session 누적인지 로그와 metric tag로 분리한다.
- 1500명 안정 구간을 포트폴리오 기준값으로 삼고, 1800명은 한계 탐색 실패 지점으로 기록한다.

## 1800명 shared k6 병목 분리 계획

1800명 단일 k6 결과만으로는 서버 한계와 k6 수신/관측 한계가 섞일 수 있으므로, 같은 단일방 1800명을 유지하고 k6만 2대로 나눠 다시 측정한다.

### 적용한 실행 방식

- profile: `infra/gcp-loadtest/profiles/hot-room-1800-shared-k6.tfvars.example`
- scenario: `k6/scenarios/08-hot-room-ramped.js`
- `shared_room_mode=true`
- k6: `e2-standard-8` x 2
- worker당 VU: `900`
- 전체 VU: `1800`
- 방 개수: `1`
- 전송 조건: `connect_ramp_seconds=120`, `chat_duration_seconds=120`, `send_interval_ms=1000`

### 변경 내용

- coordinator k6 worker가 `/api/rooms`로 방을 1개 만들고 GCS `shared-room.json`에 roomId를 기록한다.
- 다른 worker는 `shared-room.json`을 기다린 뒤 같은 roomId에 접속한다.
- k6 summary/log는 worker별로 저장하고, coordinator가 shared run 전체 DB row count를 별도로 수집한다.
- metric label은 shared run 공통 `TEST_LABEL`을 사용해서 worker별 결과와 전체 DB count를 연결한다.

### 판정 기준

| 결과 | 결론 |

| shared k6에서 ack/visible p95가 내려가고 DB count가 맞음 | 1800명 단일 k6 수신/관측 병목 가능성이 큼 |
| shared k6에서도 visible p95가 높고 `lane_done`도 상승 | 서버 WebSocket fan-out/send 병목 가능성이 큼 |
| 서버 pipeline은 낮고 k6 visible만 높음 | k6 관측 경로 병목이 아직 남아 있음 |
| DB row count와 ack count가 계속 불일치 | 증량보다 저장/ack 정합성 조사 우선 |

## 측정 신뢰도 개선

### 문제 발견

1800명 단일방에서 서버 pipeline 지표는 낮았지만 k6 visible freshness와 ack p95가 worker별로 흔들렸다.

- 서버 `lane_done` p95는 재실행 기준 `130ms`였다.
- 서버 `ws.send.duration` p95는 `0.139ms`였다.
- DB rows와 k6 ack count는 `214,870`으로 일치했다.
- 그런데 worker-1 visible p95는 `399ms`, worker-2 visible p95는 `535ms`로 갈렸다.

이 상태에서 바로 서버 튜닝으로 넘어가면, 실제 서버 병목이 아니라 부하 생성기와 관측 경로의 비용을 서버 병목으로 오판할 수 있다.

### 근거

- Grafana k6 공식 문서는 신규 WebSocket 테스트에는 `k6/websockets`를 권장한다. 현재 테스트는 기존 `k6/ws`를 사용하므로, 우선 기존 구현 위에서 관측 비용을 줄이고 나중에 `k6/websockets` 전환을 비교한다.
  참고: https://grafana.com/docs/k6/latest/using-k6/protocols/websockets/
- Slack Koi Pond는 실제 Slack 클라이언트 전체를 복제하지 않고, API 요청과 WebSocket 메시지를 수행하는 가벼운 클라이언트로 대규모 부하를 모델링한다. 이 접근은 테스트 클라이언트 자체가 병목이 되지 않게 만드는 데 초점이 있다.
  참고: https://slack.engineering/load-testing-with-koi-pond/
- Slack Real-time Messaging은 입력 메시지와 broadcast delivery를 분리해서 설명한다. 이 관점은 현재 문서의 입력 TPS, DB TPS, logical delivery TPS, physical frame TPS 분리와 같다.
  참고: https://slack.engineering/real-time-messaging/

### 적용한 개선

k6 WebSocket 클라이언트를 역할별로 나눴다.

| role | 목적 | 동작 |
| --- | --- | --- |
| `sender` | 서버에 입력 부하 생성 | 메시지 전송과 ack 측정만 수행하고 broadcast batch full parse를 하지 않는다. |
| `observer` | 사용자 체감 지연 관측 | 메시지를 보내지 않거나 낮은 빈도로 보내고, broadcast batch를 파싱해 visible freshness를 측정한다. |
| `validator` | 소량 정합성 검증 | 소수 VU만 기존처럼 full detail parse를 수행해 중복/누락/echo 검증에 사용한다. |

| `ws_message_handler_duration_ms` | `socket.on('message')` 처리 전체 시간 |

| `ws_batch_messages_per_frame` | frame 하나에 포함된 logical message 수 |
| `ws_observer_visible_samples_total` | observer가 visible freshness를 기록한 sample 수 |

- 서버 `lane_done` p95가 worst node `142.5ms`, `ws.send.duration` p95가 `0.180ms`라서 서버 WebSocket lane/send 병목으로 판정할 증거는 없다.
- 이번 실행의 입력 TPS가 이전 1800명 full-sender 실행보다 낮은 이유는 observer와 validator가 기본적으로 메시지를 보내지 않기 때문이다. 따라서 이것은 서버 처리량 증가가 아니라, 관측 경로 오염을 줄인 신뢰도 개선 결과로 기록한다.

### 판정 기준

| 결과 | 결론 |
| --- | --- |
| observer visible이 낮고 server `lane_done`도 낮음 | 기존 full-parse k6 관측 오염 가능성이 큼 |
| observer visible이 높고 handler duration도 높음 | k6 observer 처리 한계 |
| observer visible이 높고 handler duration은 낮음 | 네트워크, LB, k6 VM 수신 경로 의심 |
| server `lane_done` 또는 `send.duration` 상승 | 서버 WebSocket fan-out/send 병목 |
| DB rows와 sender ack count 불일치 | 성능 측정 중단, 저장/ack 정합성 조사 |

### 포트폴리오용 정리

이번 변경의 핵심은 성능 개선이 아니라 측정 신뢰도 개선이다.

- 부하테스트 결과가 악화됐을 때 서버 튜닝으로 바로 넘어가지 않고, 부하 생성기와 관측 경로가 결과를 오염시키는지 먼저 검증했다.
- 대규모 WebSocket fan-out에서는 입력 TPS, DB TPS, logical delivery TPS, physical frame TPS, visible freshness를 분리해 측정했다.
- 1800명 단일방에서 k6 full-parse 관측 비용이 섞이는 문제를 확인하고, sender/observer/validator 역할 분리로 병목 판정 신뢰도를 높였다.
